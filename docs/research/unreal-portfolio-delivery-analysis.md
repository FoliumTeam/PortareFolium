# Unreal 포트폴리오 전달 방식 분석

## 범위

이 문서는 공개 배포된 Unreal Engine 개발 포트폴리오 한 사례를 2026-08-10에 관찰한 기술 분석이다. 작성자 이름, 프로필, 외부 계정, 영상 식별자는 기록하지 않았다. 수치는 해당 시점의 Vercel 서울 엣지 캐시 적중 응답과 한 번의 브라우저 렌더링을 기준으로 한다.

## 핵심 결론

화면에서 GIF처럼 보이는 주요 데모는 GIF가 아니라 `<video>` 기반의 WebM 및 MP4다. WebM을 우선 제공하고 MP4를 대체 형식으로 둔 뒤, 정지 이미지와 화면 근접 감지를 결합한다. 이 조합이 빠른 첫 화면, 반복 재생, 선명도를 함께 얻는 핵심이다.

## 정보 구조와 가독성

전체 흐름은 다음과 같다.

1. 소개
2. 대표 프로젝트
3. 프로젝트 상세 사례
4. 추가 프로젝트
5. 수상 및 연락처

대표 사례는 문제, 기술적 판단, 구현, 결과, 짧은 영상 증거를 함께 제시한다. 단순 기능 목록보다 결과를 신뢰하기 쉬운 구조다. 본문은 길고 상세 구현이 한 페이지에 모여 있으므로, 처음 방문한 사람이 핵심 성과만 빠르게 훑기는 어렵다. 작은 화면에서는 좌측 목차가 사라지므로, 모바일용 요약 목차 또는 섹션 전환 수단을 제공하는 편이 낫다.

## 전달 성능

관찰한 원본 응답 크기는 초기 HTML 543B, JavaScript 298,906B, CSS 82,652B였다. 초기 HTML은 문서 metadata와 `#root`만 포함하는 client-rendered shell이며, 본문은 React JavaScript가 실행된 뒤 생성된다. JavaScript는 HTML·CSS·JavaScript 원본 합계의 약 78%를 차지한다.

한 번의 서울 엣지 캐시 적중 측정에서는 HTML 0.040초, JavaScript 0.079초, CSS 0.128초, 대표 WebM 4.80MB는 0.513초에 전송됐다. 응답에는 Brotli 압축과 Vercel cache hit가 확인됐다. 다만 정적 자산의 `Cache-Control`은 `public, max-age=0, must-revalidate`이므로, 해시 파일명 자산에 흔히 쓰는 장기 `immutable` 정책보다 재방문 캐시 효율은 보수적이다.

이 수치는 단일 회선·캐시 상태 측정일 뿐이며, 사용자별 Core Web Vitals나 모바일 저속 네트워크 성능을 증명하지 않는다.

## 동영상과 GIF

대표 동영상은 WebM 4,802,627B와 MP4 6,052,967B 대체본으로 제공된다. 상세 사례의 짧은 MP4는 대체로 약 0.4~1.2MB다. GIF도 다른 섹션에 존재하지만 파일당 약 2.7~4.7MB로, 같은 용도의 동영상보다 전달 효율이 낮다.

동영상은 같은 Vercel 배포 도메인의 `/assets/` 정적 경로에서 제공되며, 별도 동영상 서비스 iframe이 아니다. 구현은 다음 속성을 사용한다.

```html
<video autoplay muted loop playsinline preload="metadata" poster="정지-이미지">
    <source src="demo.webm" type="video/webm" />
    <source src="demo.mp4" type="video/mp4" />
</video>
```

`IntersectionObserver`가 요소가 화면 근처에 들어오면 재생하고 벗어나면 일시정지한다. 대표 영상은 controls 없이 미리보기로, 상세 증거 영상은 controls를 제공하는 방식으로 역할을 나눴다. 상세 화면의 잠재 동영상 자산은 많으므로 `preload="metadata"`가 전체 미디어 예산을 없애지는 않는다.

PortareFolium에 적용할 때는 GIF 대신 짧은 WebM과 MP4 대체본, 정지 이미지, 화면 근접 재생을 기본으로 사용한다. 각 영상은 단일 주장만 증명하고, 모바일에서는 작은 해상도·비트레이트 variant를 제공하는 것이 좋다.

## 좌측 목차

좌측 목차는 화면 너비 1440px 이상에서만 표시되는 고정 scroll spy다. 너비는 216px이며, 본문은 이를 피하도록 왼쪽 여백을 확보한다. 스크롤과 resize를 passive listener 및 `requestAnimationFrame`으로 처리하고, viewport 높이의 약 34% 지점에 해당하는 섹션을 현재 위치로 표시한다.

현재 섹션에는 `aria-current="location"`을, 현재 프로젝트에는 `aria-current="step"`을 적용한다. 프로젝트 상세 안에서는 현재 프로젝트와 세부 구현 항목을 중첩해 펼친다. 클릭 시 URL hash를 갱신하고 `scrollIntoView()`를 호출한다. 레이아웃 변화 보정을 위해 약 0.65초, 1.3초, 2.1초 뒤에도 스크롤을 재호출하는데, 사용자의 수동 스크롤을 덮을 수 있어 단일 observer 기반 보정보다 신중히 사용할 필요가 있다.

브라우저 자동 점검에서는 클릭 뒤 hash 변경은 확인했지만 해당 자동화 환경에서 스크롤 위치 변화는 재현되지 않았다. 따라서 실제 배포 환경의 스크롤 성공 여부는 이 분석만으로 단정하지 않는다. 구현 코드에서 사용한 동작 방식은 확인했다.

## 적용 원칙

- 첫 화면에는 가장 강한 결과와 짧은 증거 영상만 배치한다.
- 상세 사례는 `문제 → 판단 → 구현 → 결과` 순서를 유지한다.
- 영상에는 caption과 대체 텍스트를 제공한다.
- 정적 콘텐츠는 가능하면 SSG 또는 SSR로 제공해 JavaScript 없이도 핵심 내용을 전달한다.
- 대형 화면 목차에는 모바일용 대체 탐색 수단을 함께 제공한다.
- 동영상 총량, 모바일 variant, cache policy를 별도 성능 예산으로 관리한다.
